# WIS-012 — Investigar binding del observer de auditoría (owen-it/laravel-auditing)

**Tipo:** Bug
**Prioridad:** Alta (afecta trazabilidad y forensia de toda la app)
**Reportado:** 2026-05-07
**Detectado durante:** WIS-011 (corrección de tipo de colaboradores)

---

## Problema

El paquete `owen-it/laravel-auditing` está configurado y todos los modelos de negocio implementan `\OwenIt\Auditing\Contracts\Auditable` con el trait `\OwenIt\Auditing\Auditable`, pero **el observer no se dispara en eventos `created`, `updated` ni `deleted`**. La tabla `audits` no recibe registros aunque el código ejecute correctamente las operaciones Eloquent.

## Evidencia

### Reproducción mínima
```bash
php artisan tinker
>>> $c = \App\Models\RH\Collaborator::first();
>>> \OwenIt\Auditing\Models\Audit::where('auditable_id', $c->id)->count();
0
>>> $c->update(['type' => 'Empleado']);
>>> \OwenIt\Auditing\Models\Audit::where('auditable_id', $c->id)->count();
0   ← debería ser 1
```

### Listeners registrados
```bash
php artisan tinker
>>> count(\Event::getRawListeners()["eloquent.updated: App\\Models\\RH\\Collaborator"] ?? [])
0   ← owen-it debería haber registrado un listener aquí
```

### Verificación en tests
Durante WIS-011 (`tests/Feature/Console/FixCollaboratorTypesCommandTest.php`), las assertions que esperaban audits creados tras `update()` fallaban con `count = 0`. Las assertions que esperaban `count = 0` (dry-run, cancelación) pasaban porque cero es siempre cero.

| `AUDITING_ENABLED` en `.env` | No definido (default `true`) |
| `AuditingServiceProvider` en `bootstrap/providers.php` | No aparece (Laravel 12 usa auto-discovery vía `composer.json` del paquete) |

## Hipótesis a investigar

1. **Auto-discovery roto**: Laravel 12 cambió cómo se cargan los service providers. Verificar que `OwenIt\Auditing\AuditingServiceProvider` se registra automáticamente. Inspeccionar `bootstrap/cache/packages.php`.
2. **Trait no engancha el observer**: el trait `Auditable` debe registrar un observer en `bootingAuditable()`. Confirmar que se llama (puede haber conflicto con otros traits que sobreescriban el `boot`).
3. **Conflicto con HasUuidPrimaryKey o SoftDeletes**: el orden de los traits importa para los `boot{TraitName}`. Verificar que no haya colisión.
4. **Service provider deferred**: si está marcado como deferred y nunca se "despierta", los listeners no se registran. Forzar carga.
5. **Versión incompatible con Laravel 12**: revisar el changelog del paquete vs. la versión instalada.

## Criterios de aceptación

1. Tras un `Model::update()` en cualquier modelo Auditable, se crea un registro en la tabla `audits` con `event = 'updated'`, `old_values` y `new_values` correctos.
2. El campo `user_id` del audit se llena con el usuario autenticado (o `null` si es CLI sin `Auth::login`).
3. Los tests skipped/relajados durante WIS-011 se actualizan para verificar audits positivos:
   - `tests/Feature/Console/FixCollaboratorTypesCommandTest.php:83` (test "actualiza el tipo...") debe agregar `expect(Audit::count())->toBe(3)`.
   - Similar para "respeta institution_id...", "deduplica numdoc..." y otros tests de happy path.
4. Mismo comportamiento en otros modelos de negocio: `Contract`, `Position`, `PositionChangeHistory`, etc.
5. Test de regresión que verifique que el observer está registrado: `count(Event::getRawListeners('eloquent.updated: App\\Models\\RH\\Collaborator')) >= 1`.

## Impacto

- **Forensia**: ningún cambio en datos productivos queda registrado. Si hay disputas sobre un cambio (cargo, salario, contrato), no hay trazabilidad.
- **Cumplimiento**: ASCUN puede tener requisitos contractuales o legales de auditoría que actualmente no se cumplen.
- **WIS-011 retroactivo**: la corrección de los 53 colaboradores no quedó auditada. Una vez arreglado este ticket, evaluar si vale la pena re-correr una "corrección de auditoría" que registre manualmente el evento histórico.
